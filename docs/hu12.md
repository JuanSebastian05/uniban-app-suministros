# HU_12: consultar las recomendaciones del Equipo 2

> Implementada en el código. Las cifras de pruebas citadas en la sección de verificación son históricas. Esta revisión no hizo
> una prueba manual en dispositivo ni llamó al servicio real del Equipo 2; tampoco consultó Neon o Render. El Equipo 2 aceptó el JSON;
> se conservan consumos para posible uso futuro, se excluyen pérdidas y se incluye una ventana sintética de despacho de 10 horas.

## Historia

Como productor, quiero ver las recomendaciones de insumos generadas para mi parcela, para planificar compras y consumos con
anticipación.

### Criterios de aceptación y cómo se cumplen

Criterios tomados de `docs/requisitos/HU_y_Requisitos_Tecnicos_Equipo3.pdf`.

| # | Criterio | Implementación |
| --- | --- | --- |
| 1 | Si existen recomendaciones para una parcela, ciclo o periodo, veo insumo, cantidad, déficit o exceso, fecha prevista y observaciones. | Sección **«Recomendaciones»** del detalle de la parcela: volumen estimado (racimos), fecha límite de corte, indicador «Cumple / No cumple la ventana de despacho» y la lista de **insumos** con *Para el [fecha prevista]*, *Requerido*, *Disponible* y **Déficit** resaltado (o «Sin déficit»). La observación es `plan.reason` del Equipo 2. Se ve también la fecha de generación y el periodo. **Brechas:** el Equipo 2 **no entrega «exceso»** ni observaciones por insumo, así que no se muestran (ver abajo). |
| 2 | Si no hay recomendaciones, la app lo indica. | «Sin recomendación aún» con el botón «Solicitar recomendación». |
| 3 | La app solo muestra las recomendaciones; no calcula predicciones. | Todo viene del Equipo 2 por nuestro backend; la app solo da formato (miles, fechas, resaltado del déficit que ya viene calculado). |
| 4 | Llegan a través del backend del Equipo 3. | La app solo llama a `POST/GET /api/v1/parcels/{id}/recommendation` (RT_11); el backend consulta al Equipo 2. |

Además (pedido del 26/10): funciona **sin conexión** con la última recomendación guardada, y un botón para **solicitar o
actualizar** una nueva, con aviso de que «puede tardar hasta un minuto».

## Decisiones

| Tema | Decisión |
| --- | --- |
| Quién habla con el Equipo 2 | Solo el backend ([`contrato-equipo2.md`](contrato-equipo2.md)): prepara la solicitud, consulta el servicio con reintentos, valida la respuesta y la guarda. Sin respuesta → `503`; respuesta inválida o rechazo → `502`. |
| Sin aforamiento | **No hay recomendación.** El OpenAPI del Equipo 2 permite omitir el aforamiento, pero usaría valores de demostración (2,4 ha, confianza 0,87) y devolvería algo inventado. El backend responde `409 NO_AFORAMIENTO` sin llamarlo y la app muestra: «Esta parcela todavía no tiene aforamiento. Cuando se reciba, podrás pedir la recomendación.» |
| Síncrono | Sin modelo asíncrono. La app llama primero a `GET /health` de **nuestro** backend (despierta Render, de mejor esfuerzo) y luego al POST con **espera de lectura de 270 s solo para este endpoint** (`RecommendationApi` usa un cliente derivado; el resto sigue en 90 s). El backend despierta al Equipo 2 con su ruta `/salud` y luego envía el POST; el OpenAPI confirma que `/salud` existe. Peor caso ≈ 4 min; lo normal, menos de un minuto. |
| Aviso de espera | Mientras pide: «Pidiendo la recomendación… puede tardar hasta un minuto.» y el botón queda deshabilitado (sin doble petición). |
| Estados | Consultando (sin copia), con datos (también sin conexión), «Sin recomendación aún», pidiendo y problema. Un problema nunca oculta la última copia. |
| Mensajes de error | Sencillos, sin códigos ni «Equipo 2»: servicio no disponible, sin conexión, sesión no válida, sin aforamiento o genérico. |
| Al abrir el detalle | Se trae del servidor la última recomendación guardada (`GET`), por si se pidió desde otro teléfono; sin red se queda con la copia local. |
| Una fila por parcela | `parcel_recommendations` guarda solo la más reciente (el servidor conserva el historial). |
| Sin FK a `parcels` | La tabla local no tiene clave foránea (A-04); una prueba de migración lo comprueba. |
| Insumos | Se guardan como JSON en la fila (solo se muestran, nunca se consultan por insumo). |
| Fechas | `fecha límite de corte` llega sin zona horaria y se muestra tal cual; la de generación (con zona) se muestra en la hora del teléfono. |
| Demostración | La sesión de demostración no tiene servidor: pedir una recomendación avisa que no se pudo. |
| Fuera de alcance | Historial de recomendaciones; elegir periodo o ciclo; configurar datos operativos reales de acopio, vehículos y horario. Para la demostración se envía una ventana sintética acordada con el Equipo 2. |

## Brechas de la HU y del Equipo 2

- **«Exceso»**: la respuesta del Equipo 2 solo trae `deficit`. No se calcula en la app (criterio 3). Si se necesita, debe agregarlo el Equipo 2.
- **«Observaciones»**: solo existe `item_plan.motivo` (por qué no cumple la ventana). No hay observaciones por insumo.
- **«Ciclo o periodo»**: se muestra la recomendación más reciente de la parcela (con su periodo); no hay selector.
- **Datos operativos**: se envía una ventana sintética de 06:00 a 16:00 del día siguiente al aforamiento, según acuerdo de demostración con el Equipo 2. No es un horario real; vehículo, capacidad y acarreo siguen bajo los valores del servicio. Los insumos que devuelve son de **empaque** (cajas, cartón, bolsas), no de cultivo.
- **Inventario enviado**: el backend envía exactamente cajas, carton y bolsas. Agrega existencias de sus ubicaciones y usa saldo cero si un material todavía no se ha sincronizado desde el celular. Se omiten los demás insumos.
- **Consumos y pérdidas**: se conservan los consumos de empaque de los últimos 90 días para posible calibración futura; el Equipo 2 actualmente no los procesa. Las pérdidas ya no se incluyen en la solicitud.

## Modelo de datos

**PostgreSQL** (migración `0011_recomendaciones`, sobre la `0010`): tabla `recommendations`
`id UUID PK`, `parcel_id UUID FK → parcels.id`, `period`, `source_version` (= `version_metodo`), `generated_at`, `payload JSONB`
(la respuesta ya validada, el mismo JSON que ve la app); índice `(parcel_id, generated_at)`. Solo inserción: cada petición exitosa
agrega una fila y `GET` sirve la más reciente.

**Room** versión **7** con `AutoMigration(6 → 7)`: tabla nueva

```text
parcel_recommendations
  parcelId          TEXT PK          (sin FK a parcels)
  recommendationId  TEXT
  period            TEXT   ("2026-W44")
  generatedAt       TEXT   (ISO con zona)
  sourceVersion     TEXT
  volumeBunches     REAL
  cutDeadline       TEXT   (ISO sin zona)
  meetsWindow       INTEGER (boolean)
  reason            TEXT NULL
  suppliesJson      TEXT   ([{name, date, requiredQuantity, availableQuantity, deficit}])
```

Esquema exportado: `app/schemas/.../7.json`.

## API

| Método y ruta | Respuesta |
| --- | --- |
| `POST /api/v1/parcels/{id}/recommendation` | `201` con la recomendación nueva; `404` parcela inexistente o ajena; `409` `NO_AFORAMIENTO`; `502` `EQUIPO2_BAD_RESPONSE`; `503` `EQUIPO2_UNAVAILABLE`; `401`/`403`/`422`. |
| `GET /api/v1/parcels/{id}/recommendation` | `200` con la última guardada; `404` (`NO_RECOMMENDATION`) si no hay o la parcela no es del usuario. |

## Demostración manual

1. Con una parcela **sin aforamiento**: detalle → «Solicitar recomendación» → aviso «Esta parcela todavía no tiene aforamiento…».
2. Enviar un aforamiento (`POST /api/v1/aforamientos` con `X-API-Key`, ver [`hu09.md`](hu09.md)).
3. «Solicitar recomendación»: aparece «Pidiendo la recomendación… puede tardar hasta un minuto». Si el servicio estaba dormido puede tardar.
4. Se ve el volumen, la fecha límite de corte, «Cumple / No cumple la ventana», los insumos con el **déficit en rojo** y «Generada el…».
5. Modo avión y reabrir el detalle: se ve la última recomendación; «Actualizar recomendación» avisa «Sin conexión…».
6. Cerrar la app y abrirla sin red: la recomendación sigue ahí.
7. Con el servicio del Equipo 2 caído: «El servicio de recomendaciones no está disponible ahora…» y la copia anterior sigue visible.
