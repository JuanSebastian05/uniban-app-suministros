# HU_09: consultar el aforamiento recibido del Equipo 1

> Implementada en el código. Las cifras de pruebas citadas en la sección de verificación son históricas; esta revisión no hizo
> una prueba manual en dispositivo ni consultó Neon o Render. El usuario informó que la migración `0010` llegó a `main`.

## Historia

Como productor, quiero ver el último aforamiento de mi parcela, para conocer la estimación de plantas y área calculada
por el sistema.

### Criterios de aceptación y cómo se cumplen

Criterios tomados de `docs/requisitos/HU_y_Requisitos_Tecnicos_Equipo3.pdf`.

| # | Criterio | Implementación |
| --- | --- | --- |
| 1 | Al abrir el detalle de una parcela veo el aforamiento más reciente con fecha, área, plantas estimadas y, si existe, confianza. | Sección **«Aforamiento»** en `ParcelDetailScreen`: «Fecha del aforamiento», «Área aforada» (distinta del área de la parcela), «Plantas estimadas» y «Confianza» (porcentaje; la fila no aparece si no hay). El más reciente es el de mayor `date` (empata por `received_at`). |
| 2 | Si la parcela no tiene aforamientos, la app lo indica con un mensaje claro. | «Sin aforamiento recibido». Si no se pudo consultar y no hay copia, **no** se afirma que no hay: se muestra un error con «Intentar de nuevo». |
| 3 | Ya sincronizado, lo veo sin conexión. | La última copia vive en Room (`parcel_aforamientos`); sin red se muestra con el aviso «Sin conexión: se muestra la última copia guardada.». |
| 4 | La app no se comunica con el Equipo 1; los datos llegan por el backend. | La app solo llama a nuestro backend (`GET /parcels` y `GET /parcels/{id}/aforamiento`); el Equipo 1 escribe con `POST /aforamientos` (RT_11). |

## Decisiones

| Tema | Decisión |
| --- | --- |
| Cómo llega | Dos vías, ambas de solo lectura: **`GET /api/v1/parcels`** trae un campo nuevo `aforamiento` (nulo si no hay) en cada parcela, de modo que el refresco que ya hace la lista deja la copia al día en una sola llamada; y **`GET /api/v1/parcels/{id}/aforamiento`** lo consulta cada vez que se abre el detalle, así un aforamiento que llega con la app abierta se ve sin reiniciar. |
| Convención sin aforamiento | `GET /parcels/{id}/aforamiento` responde **404** con «La parcela no tiene aforamientos.»; una parcela inexistente **o de otro productor** responde 404 con «La parcela no existe.» (no se revela que existe). En `GET /parcels` el campo es `null`. El campo es aditivo: no rompe a clientes anteriores. |
| Una fila por parcela | `parcel_aforamientos` guarda solo el más reciente (clave: `parcelId`), no el historial. |
| Sin FK a `parcels` | La tabla no tiene clave foránea (A-04): `ParcelRepository.refresh()` borra y reinserta las parcelas. Como no se borra en cascada, `refresh()` también vacía y repuebla `parcel_aforamientos` en la misma transacción. Hay pruebas que lo verifican. |
| Estados de la sección | Consultando (primera vez, sin copia), con datos (también sin conexión), «Sin aforamiento recibido» y error con reintento. Una copia local nunca se oculta por un fallo de red. |
| Áreas | «Área aforada» es la del aforamiento (informativa, la calcula el Equipo 1); el área de la parcela sigue en el encabezado. Decisión del 26/10. |
| Formato | Fecha `dd/MM/aaaa`, área con coma («2,41 ha»), plantas con separador de miles («1.850») y confianza en porcentaje («87 %», «87,5 %»). |
| Demostración | La sesión de demostración no tiene servidor: la sección dice «Sin aforamiento recibido». |
| Fuera de alcance | Historial de aforamientos; recibirlos sin conexión por otra vía que no sea el backend. |

## Modelo de datos

**PostgreSQL:** sin cambios en este PR; usa `aforamientos` de la migración `0010`.

**Room** versión **6** con `AutoMigration(5 → 6)` (la 5 es la de HU_08): tabla nueva

```text
parcel_aforamientos
  parcelId         TEXT PK          (sin FK a parcels)
  aforamientoId    TEXT
  date             TEXT   (AAAA-MM-DD)
  areaHa           TEXT   ("2.41")
  estimatedPlants  INTEGER
  confidence       TEXT NULL ("0.870", fracción de 0 a 1)
```

Esquema exportado: `app/schemas/.../6.json`. La migración no toca los datos existentes.

## API

| Método y ruta | Respuesta |
| --- | --- |
| `GET /api/v1/parcels` | Cada parcela trae `aforamiento: { id, parcelId, date, areaHa, estimatedPlants, confidence } \| null`. |
| `GET /api/v1/parcels/{id}/aforamiento` | `200` con el aforamiento más reciente; `404` si no hay o la parcela no es del usuario; `401` sin token; `403` sin perfil; `422` si el id no es un UUID. |

`areaHa` y `confidence` viajan como texto decimal (`"2.41"`, `"0.870"`), igual que el resto de áreas de la API.

## Demostración manual

1. Con la clave de servicio configurada, el Equipo 1 (o `curl`) envía un aforamiento:
   `POST /api/v1/aforamientos` con `X-API-Key`, el `parcelId` de una parcela del productor y, por ejemplo, 1.850 plantas,
   2,41 ha y confianza 0,87.
2. App → Parcelas → esa parcela: sección **Aforamiento** con fecha, «Área aforada: 2,41 ha», «Plantas estimadas: 1.850»
   y «Confianza: 87 %».
3. Otra parcela sin aforamientos: «Sin aforamiento recibido».
4. Modo avión y reabrir el detalle de la primera: se ve el aforamiento con «Sin conexión: se muestra la última copia
   guardada.».
5. Con la app abierta, enviar un aforamiento con fecha posterior: al salir y volver a entrar al detalle se actualiza.
6. Cuenta nueva sin copia local y sin red: aparece el error con «Intentar de nuevo».
