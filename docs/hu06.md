# HU_06: sincronizar movimientos pendientes

## Alcance

Los movimientos que HU_04 guarda en Room con estado `PENDING` se envían solos al backend
FastAPI, que los guarda en PostgreSQL (Neon). La app sigue funcionando sin conexión y no
bloquea la interfaz mientras sincroniza.

```text
EntryViewModel → InventoryRepository → Room            (guardar: sin red, sin esperas)
                        │ onMovementSaved
                        ▼
              SyncScheduler (WorkManager, requiere red)
                        ▼
                    SyncWorker → MovementSyncRepository → Retrofit
                                                             ▼
                                   POST /api/v1/movements → PostgreSQL (Neon)
```

## Estados (RT_02)

| Estado | Significado |
| --- | --- |
| `PENDING` | Guardado localmente, aún no enviado. |
| `SYNCING` | Tomado por la sincronización en curso. |
| `SYNCED` | El servidor lo aceptó (201 o 200). |
| `ERROR` | El envío falló; se conserva localmente y se reintenta. |

Transiciones: `PENDING|ERROR → SYNCING → SYNCED | ERROR`. Un `SYNCING` que sobrevive a un
cierre de la app vuelve a `PENDING` al inicio de la siguiente pasada. Si WorkManager cancela
el trabajo durante un envío, el movimiento vuelve a `PENDING`. Sincronizar no modifica el
contenido del movimiento ni la existencia local.

## Cuándo se sincroniza

- Al abrir la app y cada vez que se guarda una entrada: se encola un trabajo único que se
  ejecuta cuando hay conexión (`NetworkType.CONNECTED`).
- Fallo de red, tiempo agotado, 408, 429 o 5xx: el movimiento pasa a `ERROR`, se detiene la
  pasada (el resto sigue `PENDING`) y WorkManager reintenta con espera exponencial (30 s inicial).
- Rechazo del servidor (409, 422…): pasa a `ERROR` y no se pide reintento inmediato; queda para
  la siguiente pasada (al abrir la app, al guardar otro movimiento o en el trabajo periódico de 15 min).

## Contrato: `POST /api/v1/movements`

JSON camelCase. Cada movimiento viaja con el contexto de su inventario; el backend inserta
productor, ubicación, insumo e inventario **solo si no existen** y nunca los sobrescribe.

```json
{
  "id": "uuid-del-movimiento", "type": "ENTRADA", "quantity": 1.50,
  "date": "2026-09-29", "observation": "compra",
  "createdAt": "2026-09-29T21:40:00.123Z", "updatedAt": "2026-09-29T21:40:00.123Z",
  "inventory": {
    "id": "uuid", "initialQuantity": 120.00,
    "location": { "id": "uuid", "name": "Inventario principal",
                  "producer": { "id": "uuid", "name": "Productor de demostración" } },
    "supply": { "id": "uuid", "name": "Fertilizante 15-15-15", "category": "Fertilizante", "unit": "kg" }
  }
}
```

| Respuesta | Significado |
| --- | --- |
| `201 {"status": "CREATED"}` | Guardado; la existencia del servidor aumenta. |
| `200 {"status": "DUPLICATE"}` | Ya existía idéntico: no se duplica ni se vuelve a sumar (RT_07). |
| `409` | Mismo UUID con contenido distinto, tipo no soportado (solo `ENTRADA` por ahora) o existencia > 99.999,99. |
| `422` | Datos inválidos (cantidad ≤ 0, más de dos decimales, UUID inválido…). |

En PostgreSQL la existencia es `inicial + movimientos recibidos` y se actualiza en la misma
transacción que el movimiento (RT_10). Los movimientos son solo de inserción.
Sin verificación de identidad todavía: HU_01 y RT_13 siguen pendientes.

## Configurar y ejecutar en local

1. **Base en Neon.** Copiar la cadena de conexión (Console → *Connect*) a `backend/.env`:
   `DATABASE_URL=postgresql+psycopg://USUARIO:CLAVE@HOST/BASE?sslmode=require`.
2. **Backend** (desde `backend/`):

   ```powershell
   python -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt
   alembic upgrade head          # crea las tablas en Neon
   uvicorn app.main:app --reload
   ```

3. **App:** con `api.baseUrl=http://10.0.2.2:8000/` (valor por defecto) el emulador llega al
   backend local. Ejecutar la configuración `app` en Android Studio.

## Verificación

Backend (no requiere Neon; usa SQLite en memoria): `cd backend && pytest`.
App: `.\gradlew.bat testDebugUnitTest` desde `android-app` (ver [HU_04](hu04.md) para JDK y rutas con tildes).
Las pruebas de la app cubren: envío y paso a `SYNCED`, fallo de red → `ERROR` y reintento,
rechazo del servidor, recuperación de `SYNCING`, cancelación, no reenviar `SYNCED` y el disparo
tras guardar. Las de PyTest cubren creación, doble envío del mismo UUID, conflictos, validación
y límites.

## Demostración manual (criterios de aceptación)

1. Con el backend apagado o en modo avión, registrar una entrada: queda «Pendiente de sincronización».
2. Levantar el backend / quitar el modo avión: en segundos el movimiento pasa a «Sincronizado»
   sin intervención (criterios 1 y 2). El contador de pendientes vuelve a cero.
3. Con el backend apagado pero la app con red, el movimiento pasa a «Error al sincronizar · se
   reintentará» y conserva su dato (criterio 3); al levantar el backend se sincroniza.
4. Cerrar la app durante un envío y volver a abrirla: el movimiento se retoma (criterio 5).
5. En Neon (SQL Editor): `SELECT * FROM movements;` muestra el movimiento y
   `SELECT quantity FROM inventory;` la existencia local (criterio 6). Reenviar el mismo UUID
   no crea otra fila (criterio 4).
