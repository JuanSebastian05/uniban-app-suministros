# HU_15: registrar cosecha real por recomendación semanal

> Implementada en código local el 28/10/2026. Requiere backend con Alembic **0013** y Android con Room **11**. La puesta en producción se verifica por separado.

## Historia

Como productor, quiero confirmar los racimos realmente cosechados contra la recomendación semanal de mi parcela, para conocer el avance del plan y disponer de un saldo real para despachar.

## Criterios de aceptación

| Criterio | Implementación |
| --- | --- |
| Registrar únicamente durante Producción. | Room valida el ciclo y la etapa de la fecha elegida; el servidor vuelve a validar con el historial de etapas. Siembra pasa a requerir En preparación. Las demás actividades conservan sus reglas. |
| Requerir parcela, ciclo, aforamiento y recomendación asociados. | Se conserva la procedencia de las recomendaciones nuevas. El formulario usa una referencia archivada que no desaparece al actualizar la recomendación visible. El servidor comprueba todas las relaciones y el productor. |
| Mostrar la sugerencia y registrar la realidad. | Se distinguen estimación semanal decimal y carga entera del plan. La cantidad real es un entero positivo, editable; fecha y observación opcional quedan registradas. No se vuelve a aplicar la confianza. |
| Admitir parciales sin renovar el cupo. | La clave de avance es parcela + `period`. La primera cosecha fija la recomendación de origen del periodo. Una recomendación nueva del mismo periodo no suma otro cupo. |
| Permitir una excepción explícita. | Cada cosecha que supera la estimación acumulada requiere marcar la confirmación. La confirmación se guarda en Room y en el backend. |
| Mostrar el pendiente. | La pantalla muestra cosechados, despachados, disponibles, estimación pendiente y carga pendiente de despacho. |
| Integrar COSECHA sin duplicar. | Una misma operación usa un UUID para `activities.id` y `harvests.id`. El backend guarda ambas filas en una transacción; WorkManager envía solo la operación estructurada. |
| Funcionar offline. | UUID del dispositivo, escritura Room primero, estado PENDING y sincronización posterior. El UUID y los campos del formulario se conservan en SavedStateHandle al recrearlo. |

## Periodo y ejemplo

La solicitud ya calculaba `periodo` como semana ISO de **la fecha del aforamiento**. La respuesta se guarda con **el periodo que devuelve el Equipo 2**, que el código existente permite que sea distinto. Se conserva el formato `AAAA-Wnn` y ese comportamiento: repetir una solicitud con el mismo periodo recibido no crea otro cupo. La fecha real de ejecución puede ser posterior y mantiene su periodo de origen. Falta confirmar con el Equipo 2 la semántica cuando responde una semana diferente de la enviada; la app no la reinterpreta ni cambia la ventana sintética.

Con `volumeBunches = 145.6` y carga del plan `146`, se muestran ambos valores. Sin excepción se pueden acumular hasta 145 racimos enteros; acumular 146 requiere confirmación. No se modifica `estimatedPlants` ni se genera saldo por recibir un aforamiento.

## Modelo y API

- PostgreSQL: `harvests` con PK/FK `id → activities.id`, parcela, ciclo, recomendación, aforamiento, periodo, cantidad, fecha, confirmación y payload original. Las recomendaciones nuevas conservan `aforamiento_id` y `cycle_id`; las históricas quedan nulas.
- Room: `production_plans` conserva los DTO de origen; `harvests` conserva los datos reales y su estado. Las tablas nuevas no tienen FK hacia parcelas que se reemplazan durante un refresco.
- `POST /api/v1/harvests`: 201 creada, 200 reintento idéntico, 409 conflicto de UUID/etapa/cupo/pertenencia, 422 campos inválidos. `GET /api/v1/production/{parcelId}` devuelve operaciones y recomendaciones de origen sin llamar al Equipo 2.
- [Contrato OpenAPI propio](api/production.openapi.json), [decisiones](cosecha-despacho-diseno.md), [MER](modelo-datos/MERv2.drawio).

## Compatibilidad y límites

Las actividades COSECHA antiguas se conservan como historial, sin inventar cantidades ni saldo. Una cosecha genérica nueva no se acepta por `/activities`; la interfaz lleva al formulario estructurado. Si una COSECHA antigua aún estaba pendiente, queda visible con el error que pide registro estructurado: no se convierte automáticamente ni se adivina su cantidad.

Las recomendaciones anteriores a 0013 se conservan. Para una primera operación nueva hace falta solicitar una recomendación con procedencia explícita; no se asigna retrospectivamente el último aforamiento a una recomendación antigua.

## Verificación y demostración

Pruebas: `backend/tests/test_production.py`, `ProductionRepositoryTest`, `ProductionViewModelTest`, `ProductionScreenTest` y migración 10→11. La verificación consolidada está en [estado del proyecto](estado-proyecto.md).

1. Tener una parcela en Producción, un aforamiento y una recomendación nueva.
2. Entrar por **Parcela → Cosechas y despachos**, por **Actividades → Cosechas y despachos** o elegir Cosecha en Registrar actividad.
3. Registrar 100 racimos y comprobar avance y una sola actividad COSECHA.
4. Registrar otros 45; intentar uno más sin confirmación y luego confirmar la excepción.
5. Actualizar el aforamiento/recomendación del mismo periodo: el avance y la referencia original deben mantenerse.
6. Repetir sin conexión y recuperar la conexión. Un reintento no debe duplicar la actividad ni el saldo.

No se han aplicado migraciones a Neon ni probado estas pantallas con una cuenta real en un celular.
