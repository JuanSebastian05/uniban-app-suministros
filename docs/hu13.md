## Historia

Como productor, quiero crear mi cuenta desde la app con mis datos básicos, para empezar a registrar
mis insumos sin depender de un administrador.

### Criterios de aceptación y cómo se cumplen

## Documento de identidad único (criterio 3)

Antes del 21/10/2026 nada impedía que dos cuentas usaran el mismo documento: la columna
`users.document` no era única y el backend no lo comprobaba (y una prueba lo daba por bueno).

| Tema | Decisión |
| --- | --- |
| Qué se compara | `document_key`: el documento **solo con letras y números, en mayúsculas**. «1.020.304.050», «1 020 304 050» y «1020304050» son el mismo documento; «ab-123» y «AB 123» también. El documento se guarda tal como lo escribió el productor, recortado. |
| Dónde se impone | En el servicio (`register_user`, 409 antes de crear nada) **y** en la base (restricción única `uq_users_document_key`, que cubre la carrera de dos registros simultáneos). |
| Documento sin letras ni números | `422` («---», «...»): no hay nada con qué comparar. |
| Reintento de la misma cuenta | Sigue siendo idempotente por `firebase_uid`: devuelve `200` con su perfil aunque reenvíe su propio documento con otro formato. |
| Cuentas anteriores con documento repetido | **No se borran ni se bloquean.** La migración rellena `document_key` por orden de creación: la cuenta más antigua conserva la clave y las repetidas quedan con `document_key` nulo (PostgreSQL admite varios nulos en una restricción única). Solo afecta a cuentas de prueba. |
| Qué ve el usuario | La cuenta de Firebase recién creada se elimina (flujo existente de HU_01) y el formulario conserva los datos para corregir el documento. |

## API

`POST /api/v1/users/register` (token de Firebase en `Authorization`):

| Respuesta | Cuándo |
| --- | --- |
| `201` | Perfil creado. |
| `200` | La cuenta ya estaba registrada (idempotente). |
| `409` | `detail.code` = `DUPLICATE_DOCUMENT`: otra cuenta ya usa ese documento. Cuerpo: `{"detail": {"code": "DUPLICATE_DOCUMENT", "message": "Ya existe una cuenta con este documento."}}`. |
| `422` | Datos inválidos, documento sin letras ni números, o token sin correo. |
| `401` | Sin token válido. |

El `409` es nuevo: ningún otro cliente lo usa hoy (solo la app Android).

## Base de datos: migración histórica `0007_documento_unico`

Agregó `users.document_key` (VARCHAR 30, única, admite nulos) y la rellenó. La base central debe conservar esa

`alembic check` sin diferencias con los modelos y `downgrade`/`upgrade` reversibles.

## Demostración manual

1. Registrar «Ana» con documento `1020304050` → entra al inventario.
2. Cerrar sesión. Crear otra cuenta con otro correo y documento `1.020.304.050` → «Ya existe una cuenta
   con este documento…», los campos siguen escritos y no se crea la cuenta (tampoco en Firebase).
3. Corregir el documento → se crea la cuenta.
4. Crear otra cuenta con el correo de Ana → «Ya existe una cuenta con este correo».

## Robustez del registro (P-02, 21/10/2026)

Dos fallos que no eran del criterio 3 pero rompían el registro en la práctica; el detalle técnico está en
[`hu01.md`](hu01.md#cuenta-sin-perfil-cuenta-huérfana-p-02):

- **Cuenta huérfana:** si la app se cerraba entre crear la cuenta en Firebase y guardar el perfil (o el borrado
  de la cuenta fallaba), ese correo quedaba sin perfil —403 en todo— y no podía volver a registrarse. Ahora la
  app pregunta `GET /users/me` al abrir sesión; si responde 404 lleva a «Complete su perfil», que envía el
  perfil con el mismo `POST /users/register` (idempotente, y con el mismo `409 DUPLICATE_DOCUMENT`).
- **Primer registro tras el sueño de Render:** el servidor tarda cerca de un minuto y el tiempo de espera era
  de 30 s. Ahora la lectura espera 90 s, la app despierta el servidor al abrirse y el formulario avisa que
  puede tardar.
