# HU_08: registrar actividad productiva

> Implementada en el código. La verificación automática citada abajo corresponde al 24/10/2026; la demostración manual en dispositivo
> y el estado de producción deben confirmarse por separado. La cabeza local de Alembic está ahora en `0012`.

## Historia

Como productor, quiero registrar actividades como siembra, fertilización o cosecha, para asociar los consumos
de insumos a cada etapa del cultivo.

### Criterios de aceptación y cómo se cumplen

| # | Criterio | Implementación |
| --- | --- | --- |
| 1 | Elijo parcela y ciclo; indico tipo, fecha y observaciones opcionales. | Formulario «Registrar actividad»: usa el ciclo activo o, durante el descanso, el último ciclo cerrado. Una parcela que nunca ha iniciado un ciclo aún no puede asociar actividades. |
| 2 | Puedo asociarle consumos de insumos en el mismo flujo. | Bloque «Insumos usados»: filas de insumo + cantidad. Cada fila se guarda como un **CONSUMO** de esa parcela y ciclo, ligado a la actividad, en la **misma transacción de Room**. |
| 3 | Sin conexión, se registra localmente y queda pendiente. | Todo nace en Room con UUID y `PENDING`; las actividades se sincronizan **antes** que sus consumos (HU_06). El contador de pendientes suma actividades y movimientos. |
| 4 | Visible en el detalle de la parcela y en el historial de los insumos asociados. | Detalle de la parcela: sección **«Actividades»**. Historial (HU_07): cada consumo de una actividad muestra «Actividad: …». Además, pestaña **Actividades** con la lista completa. |

## Decisiones

| Tema | Decisión |
| --- | --- |
| Tipos | Los del mockup: Fertilización, Siembra, Cosecha, Aplicación de insumo, Control fitosanitario y Otra actividad (`FERTILIZACION`, `SIEMBRA`, `COSECHA`, `APLICACION_INSUMO`, `CONTROL_FITOSANITARIO`, `OTRA`). La HU nombra también «producción»: no es un tipo propio, es el estado del ciclo. |
| Ciclo | **Obligatorio**: la actividad cuelga de un ciclo (MER). En descanso se asocia al último ciclo cerrado; si nunca se inició un ciclo, la app lo indica. El backend acepta ciclos cerrados para soportar actividades sincronizadas o registradas durante el descanso. |
| Avisos por etapa | Siembra en Producción/Descanso y cosecha en Preparación/Descanso muestran un aviso orientativo. El productor puede continuar; todavía no hay bloqueos por etapa. |
| Todo o nada | Si algún insumo no alcanza (`ActivityStockException`) no se guarda ni la actividad ni los demás consumos; la fila afectada muestra el error. |
| Reintento | Los consumos usan un UUID derivado de la actividad y el insumo: guardar dos veces el mismo formulario no duplica ni resta dos veces. Mismo UUID con otros datos se rechaza. |
| Insumos repetidos | No se permite el mismo insumo en dos filas (se sumaría en una sola). |
| Ciclo del consumo | El consumo de una actividad usa el ciclo **de la actividad**, aunque después la parcela cambie de ciclo. |
| Sincronización | `MovementSyncRepository` envía primero las actividades (`POST /api/v1/activities`) y luego los movimientos; un consumo cuya actividad aún no está `SYNCED` espera en `PENDING`. Si el servidor rechaza la actividad, sus consumos no se envían. |
| Sin FK a `parcels` | `activities` no tiene clave foránea hacia `parcels` (regla de A-04): `ParcelRepository.refresh()` borra y reinserta las parcelas; hay una prueba que lo verifica. |
| Fuera de alcance | Editar o borrar actividades; `GET /activities` para el Equipo 2; mostrar la actividad en el detalle de cada insumo (solo en el historial). |

## Modelo de datos

**PostgreSQL** (migración `0009_actividades`, sobre la `0008` de ajustes):

```text
activities
  id           UUID PK
  parcel_id    UUID FK → parcels.id           (índice)
  cycle_id     UUID FK → production_cycles.id
  type         VARCHAR(30) CHECK (los seis tipos)
  date         DATE
  observation  VARCHAR(500) = ''
  created_at, updated_at, received_at
movements.activity_id  UUID NULL FK → activities.id   (índice; solo consumos)
```

**Room** versión **5** con `AutoMigration(4 → 5)`: tabla `activities` (sin FK) y `movements.activityId` nula.
Esquema exportado: `app/schemas/.../5.json`.

## API

`POST /api/v1/activities` (token de Firebase; idempotente por UUID):

| Respuesta | Cuándo |
| --- | --- |
| `201` | Actividad creada. |
| `200` | Ya existía idéntica (`status: DUPLICATE`). |
| `409` | Mismo UUID con otro contenido o de otro productor, parcela inexistente o de otro usuario, o ciclo que no es de la parcela. |
| `422` | Tipo desconocido, observación de más de 500 caracteres, falta `cycleId` o fecha inválida. |
| `401` / `403` | Sin token válido / cuenta sin perfil. |

`POST /api/v1/movements` acepta `activityId` (solo en `CONSUMO`): la actividad debe existir, ser del productor y
**coincidir en parcela y ciclo** con el consumo (409 si no); en otros tipos → 422.

```json
{ "id": "…", "parcelId": "…", "cycleId": "…", "type": "FERTILIZACION",
  "date": "2026-10-24", "observation": "Primera aplicación",
  "createdAt": "2026-10-24T10:00:00.000Z", "updatedAt": "2026-10-24T10:00:00.000Z" }
```

## Demostración manual

1. Parcelas → una parcela **con ciclo** → «+ Registrar actividad» (o pestaña **Actividades** → «+ Registrar actividad»).
2. Guardar sin elegir tipo ni parcela → errores junto a cada campo.
3. Elegir parcela, **Fertilización**, hoy, observación «Lote norte» y agregar insumo **Urea 46%** 12,5 kg → guardar.
   Vuelve al detalle: aparece la actividad «Fertilización · 1 insumo usado · Pendiente de sincronización».
4. Inventario → Urea: la existencia bajó 12,5 kg. Historial: el consumo muestra «Actividad: Fertilización».
5. Intentar un insumo con más cantidad que la existencia → error en esa fila y **no** se guarda la actividad.
6. Una parcela **sin ciclo**: el detalle dice que se inicie un ciclo y el formulario avisa.
7. Modo avión: registrar otra actividad → queda pendiente (contador); al volver la red pasa a «Sincronizado» y
   en la base `activities` y `movements.activity_id` quedan enlazados.
